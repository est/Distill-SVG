# 截图 → SVG：调研、算法与项目设计

> 目标：把 GUI 截图重构成一个**不含整张原始位图**的 SVG：纯色块/线框、可复制文本、少量矢量图标；照片/头像可按开关嵌入裁剪。
> 允许纯色，不处理渐变/阴影/毛玻璃；但画布尺寸、面板位置、文字基线要尽量准。
>
> 本文基于仓库里的两张本地测试图（`tests/1.png`、`tests/2.jpg`，已加入
> `.gitignore`，不进入 git）和当前 `caption_svg` 原型写成。

---

## 0. TL;DR

- **不要做“位图描摹”，要做“语义重绘”**。纯 tracer（vtracer/potrace）会把文字也变成
  路径、把噪点/水印保留下来，文件还大；LLM 截图转 HTML 又不够精确、隐私不可控。
- 推荐 **混合管线**：
  1. 去抖/降采样/调色板量化（破坏像素级隐写通道）；
  2. 用 OCR 得到行级文本与框；
  3. 用颜色连通域恢复圆角面板/气泡/卡片；
  4. 用高方差残差找图标/emoji/照片；图标做分色描摹，照片/头像默认嵌入裁剪（隐私模式变占位块）；
  5. 用“墨迹框 + 字宽 + 字体度量”反推字号/基线，而不是相信 OCR 框高度；
  6. 输出 `<rect>` + `<text>` + `<path>` 的自包含 SVG。
- 两张测试图的结果：嵌入照片后 SVG 76 KiB / 111 KiB；把 SVG 重新栅格化再 OCR，
  文本行中心误差中位数 **1.5 px / 3.6 px**，文本相似度 **0.988 / 0.980**（hybrid OCR）。
- 最大的三个坑不是 SVG 语法，而是：
  1. **OCR 的中文/混合排版与置信度**（需要人工校正入口）；
  2. **字体识别与跨平台还原**（PingFang/Noto/厂商字体，字重、基线、字距）；
  3. **图标/emoji/头像的语义分类**（描摹、图标库吸附、还是占位）。

## 1. 背景、目标与非目标

### 1.1 为什么要“重绘”而不是“压缩”

截图文件里除了可见内容，还可能带：

- 像素级抖动/噪声（测试图 `1.png` 就是典型：平坦区域被 ±1~2 的棋盘噪声覆盖）；
- LSB 隐写、频域水印、设备/应用指纹；
- EXIF、文件名、剪贴板/分享链路信息；
- 原始照片、头像、二维码等高风险内容。

把截图转成“几何 + 文本”的重绘结果，会**丢弃原始像素网格**，因此大多数像素级
隐写通道无法原样存活。注意：这不等同于“匿名化”，见第 6 节。

### 1.2 目标

- 输入一张 GUI 截图，输出单文件 SVG；
- 保留：画布尺寸、主要面板/气泡/卡片、文字内容与位置、文本颜色、图标位置；
- 允许：纯色填充、圆角、1px 描边；
- 不处理：渐变、阴影、模糊、复杂纹理；
- 不嵌入整张原始位图；照片/头像可选嵌入小裁剪，不引用外部资源；
- 可编辑：文本仍是文本（可选转 path），中间 scene JSON 可人工修正。

### 1.3 非目标（v0）

- 像素级还原（SSIM > 0.99）；
- 自动修复 OCR 错字；
- 自动完美还原照片/头像的原始无损质量（裁剪框是启发式，可能略紧/略松）；
- 支持所有设计工具/所有 SVG 渲染器的字体一致性；
- 移动端 App 的实时截图管线。

## 2. 测试图观察（决定了算法）

### 2.1 `tests/1.png`：低分辨率截图 + 2x 最近邻放大 + 抖动

| 指标 | 值 |
| --- | --- |
| 文件尺寸 | 602 × 842 |
| 唯一颜色数 | 5,083 |
| 覆盖 99% 像素的颜色数 | 1,571 |
| 最常见颜色 | `(243,244,245)`、`(241,242,243)`、`#fff`、`(253,253,253)`、`(213,230,255)`… |
| 2×2 像素块完全一致比例 | 92.1% |
| 水平相邻像素对一致比例 | 94.7% |

关键发现：

1. 背景不是 `#F3F4F5`，而是在 `239/241/243` 之间抖动的 2×2 棋盘；
2. 蓝色气泡也是 `211/213` 两套值交替；
3. 2×2 块高度一致，说明这张图很可能是 **301×421 的逻辑截图被 2× 最近邻放大**，
   抖动发生在逻辑像素层；这也解释了为什么“缩到一半”后文字反而更干净。
4. 直接做 k-means 会得到大量近色簇；必须先做**条件中值滤波**（只替换局部平坦像素），
   再量化。

### 2.2 `tests/2.jpg`：1080×2306 的 Android/高 DPI 截图

| 指标 | 值 |
| --- | --- |
| 文件尺寸 | 1080 × 2306 |
| 唯一颜色数 | 45,456 |
| 覆盖 99% 像素的颜色数 | 20,552 |
| 主背景 | `(241,245,248)` |
| 文本墨迹高度 | 约 42–45 px |
| 反推字号 | 约 45 px ≈ 15 sp @3x |
| 逻辑尺寸 | 约 360 × 769 |

关键发现：

- JPEG 块效应 + 抗锯齿让“平坦区域”不唯一，但整体仍可量化；
- Vision OCR 给出的行框高度约 50–66 px，**明显大于墨迹高度 42–45 px**；
  如果直接用 OCR 框高度估字号，会偏大 15–40%；
- 中文正文以行级 OCR 为主，英文/数字混排时行框会被拉高，必须用**墨迹框**修正。

### 2.3 对算法的直接结论

1. **先检测/消除放大与抖动**：分析尺度用 2x 降采样（`--scale 2`），条件中值滤波；
2. **颜色量化到 10–20 个簇**即可覆盖面板；不要试图保留所有抗锯齿色；
3. **字号用墨迹宽度拟合，不用 OCR 框高度**；
4. **基线用字体 ascent 与墨迹 bottom 反推**；
5. **照片/头像要从形状层剥离**：嵌入时只嵌入裁剪，不把整张截图重新编码；否则路径巨大且会泄露整屏内容。

## 3. 方案选型：为什么不直接 tracer / 不直接 LLM

| 方案 | 代表 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| 纯位图描摹 | vtracer、potrace、ImageTracer | 颜色/形状还原好，工程简单 | 文字变路径不可编辑；噪点/水印被保留；照片路径巨大；文件可能比 PNG 还大 | 仅适合图标/logo 局部 |
| LLM 截图转 HTML/SVG | screenshot-to-code、GPT-4V 类 | 语义好，能“理解”界面 | 坐标/字号不精确；中文小字易错；云端隐私风险；不可复现 | 不适合作为几何引擎，可做辅助识别 |
| 可微矢量 | diffvg、LIVE、StarVector | 研究前沿，端到端 | 训练/推理重；对 UI 文本/精确布局不友好 | 暂不采用 |
| **语义重绘（本方案）** | 本原型 | 小、可编辑、隐私友好、坐标可控 | 依赖 OCR/字体/图标分类 | **推荐** |

更准确地说：**面板用矩形，文字用文本，图标用局部描摹，照片/头像用裁剪嵌入（或隐私占位）**。
每一类元素用最适合它的表示，而不是全图一种算法。

### 4.1 预处理（`caption_svg/flatten.py`）

- **条件中值滤波**：3×3 中值只在局部极差 ≤10 时替换。这样能抹掉抖动，又不会
  把 1px 文字笔画/图标线条一起抹掉。
- **Lab k-means**：`k=14` 左右。对 2x/3x 截图先降采样到分析尺度，减少噪声和计算量。
- **调色板颜色**：面板填充取连通域内像素的中位数，并四舍五入到偶数（进一步去抖）。
- 注意 `255` 四舍五入到偶数会变成 `256`，必须 `clip(0,255)`（原型踩过这个坑，
  生成了非法颜色 `#fcfe100`，浏览器把它当黑色）。

### 4.2 面板/气泡/卡片（`caption_svg/panels.py`）

思路：同一调色板颜色的连通域，通常就是一个面板。文字/图标会在面板里打洞，所以：

- 用 `extent = area / bbox_area` 允许低到 0.45；
- 用凸包 `solidity` 允许低到 0.52；
- 过滤细长文字行（长宽比 > 18）；
- 角半径用四个角 10×10 窗口的“空面积”估计：
  `empty ≈ r²(1-π/4)`，再取中位数并 clamp；
- 用几何近似去重（抗锯齿会产生同位置、不同颜色的多个簇）；
- 面积大的先画，小的后画（z-order）。

细线/分隔线/卡片边框由 `caption_svg/strokes.py` 补充：用局部背景对比 + 方向形态学
提取 1–2px 线，过滤文字/照片区域，合并共线段；`--strokes auto` 只保留长分隔线/边框，
`all` 才包含下划线和进度条。单张 1080×2306 约 50ms。

这一层已经能覆盖聊天页 80% 的视觉结构。剩余难点是：

- 阴影/描边：用 1px 半透明描边近似；
- 同色嵌套面板：会被去重掉（视觉上不可见，通常没问题）；
- 小圆钮/胶囊：面积阈值和角半径估计会略保守，原型里偶尔漏掉。

### 4.3 文字：OCR 只是“候选”，几何要从像素反推（`caption_svg/fonts.py`）

对每一行 OCR：

1. **取墨迹框**：在 OCR 框附近估计背景色（中位数），把颜色距离 >38 或显著更暗的
   像素当墨迹；去掉孤立噪点，限制在 OCR 框 ±1px 内。
2. **拟合字号**：用字体的 `getbbox(text)` 在 100px 下的墨迹宽度做线性缩放：
   `size = target_ink_width * 100 / ink_width_100`。
   - 不要用 OCR 框高度：Vision 的行框带 padding，`2.jpg` 里高度 50.5 对应墨迹 43；
   - 对纯 CJK，字宽几乎严格等于 1em，宽度拟合很稳；
   - 对含空格的英文行，先 strip 首尾空格。
3. **反推基线**：`baseline = ink_bottom - (bbox_bottom - ascent)`；
   其中 `bbox` 是字体在原点左上角的墨迹框，`ascent` 来自 `getmetrics()`。
4. **颜色**：取墨迹像素中亮度最低的 20% 的中位色；避免抗锯齿把颜色冲淡。
5. **字体/字重**：候选字体逐个渲染，按“墨迹框对齐后的 IoU − 密度差惩罚”打分；
   按整张图的加权投票选一个字族，再在族内选字重。
6. **清理 OCR 垃圾**：去掉 `EQ`、`2Q`、`©` 这类图标误识别；去掉尾部 `|v`；
   去掉零宽字符；平衡括号。

原型里一个重要的经验：**CJK 的字宽不能用来区分字体**（PingFang/Noto/Source Han
的汉字 advance 基本都是 1em）。必须比较字形掩码；但字重会被抗锯齿光晕干扰，
所以加了“墨迹密度”惩罚，并对小字号限重（<15px 最多 500）。

### 4.4 字体渲染还原（重点）

这是“看起来像不像”的核心，方案有三层：

| 方案 | 一致性 | 可编辑 | 体积 | 授权 |
| --- | --- | --- | --- | --- |
| `font-family` 栈 | 低（取决于查看器/系统） | ✅ 文本可复制 | 最小 | 无额外问题 |
| 嵌入 subset font（WOFF2 base64） | 中高 | ✅ | 中（几十 KB） | 字体必须可再分发（Noto/Source Han OFL；PingFang 不行） |
| 文本转 path | 最高 | ❌ 不可编辑/不可搜索 | 大 | 仍受字体授权约束 |

建议：

- **默认 `text` + font stack**，适合浏览器/Figma 快速查看；
- 提供 `--text=path`：用匹配到的字体把每行转 `<path>`，适合归档/跨平台一致；
- 提供 `--embed-font`：只对 OFL 字体做 subset；不要嵌入 PingFang/微软雅黑；
- 输出时用 `textLength`/`lengthAdjust="spacing"` 只在宽度偏差 >2% 时兜底，
  避免中文被拉变形。

还需要处理的细节：

- **基线**：SVG 的 `y` 是基线，不是 top；不要用 `dominant-baseline` 赌渲染器；
- **字距**：中文 UI 通常 0；英文可能有 tracking，可用 `letter-spacing` 拟合；
- **行高**：OCR 已经给了每一行，不要重新排版/折行；
- **Hinting/亚像素**：低分辨率截图里的字形和浏览器 1x 渲染不完全一样，
  用 2x/3x 渲染再缩小的方式比较更公平；
- **平台差异**：iOS PingFang SC，Android Noto Sans CJK/Roboto，Windows 微软雅黑，
  很多 App 还会自带字体。字体识别只能“候选匹配”，不能保证 100%。

### 4.5 照片、头像、图标、emoji（`caption_svg/images.py`）

用“残差”找内容：

```
residual = 颜色距离(像素, 面板/背景调色板) > 14
         OR 5×5 局部标准差 > 14
```

然后：

- **文字框内**的残差清零（文字交给文本层）；
- **面板边界** 2px 清零（圆角边缘方差高，会把头像和气泡连成一块）；
- 连通域后按 bbox/密度/颜色多样性分类。

照片/头像判定（启发式）：

- 大区域（≥34×34 分析像素，面积 ≥3000）→ 照片；
- 靠左右边缘、尺寸 ≥14、颜色多样（top-5 颜色覆盖 <50%）、密度 ≥0.35 → 头像；
- 小卡片里的扁平图标（top-5 覆盖高）→ 图标；
- 照片 bbox 会再按“内容像素”收紧，避免 party hat/阴影把框撑大。

图标描摹：

1. 裁小图，必要时 2–4× 插值放大；
2. Lab k-means 压到 1–6 色；
3. 跳过与面板/背景同色的层（否则会画出大块浅色矩形）；
4. 每层 `findContours(RETR_CCOMP)` + `approxPolyDP`，用 `fill-rule="evenodd"` 保留孔洞；
5. 限制每层点数/总路径数。

emoji 目前就是“彩色小图标”，同样走描摹；识别成 Unicode 再用系统 emoji 字体是后续方向。

照片/头像的两种策略：

- `--photos embed`（默认）：用未收紧的组件 bbox 从**原图**裁剪，重新编码为 PNG/JPEG
  后写成 `data:` URI。重新编码不会复制源文件 EXIF，但会保留裁剪区域里的像素
  （包括潜在的像素级水印）。这是“还原优先”模式。
- `--photos placeholder`：只画中性色块 + glyph，不嵌入任何照片像素。这是隐私模式。
- `--photos outline`：只画空框，适合纯线框/审查。
- `--photo-scrub`：嵌入前丢弃每通道低 2 bit，视觉上接近无损，但能破坏常见
  LSB 隐写；它不是“匿名化”，也不会去除频域水印。
- 嵌入照片内部的 OCR 文本（如商品图标题）默认从文本层移除，避免与图片内容重复；
  代价是这些字不可单独选中。需要保留时用 `--keep-photo-text`。
- 裁剪框是启发式的：party hat、徽章、阴影可能让框略紧或略松；后续可以用面板/圆角
  检测或用户拖框修正。

### 4.6 SVG 序列化（`caption_svg/svg.py`）

```xml
<svg width="1080" height="2306" viewBox="0 0 1080 2306">
  <rect .../>                     <!-- 背景 -->
  <g id="panels">…</g>            <!-- 卡片/气泡 -->
  <g id="images">…</g>            <!-- 裁剪 <image> / 占位块 / 空框 -->
  <g id="icons">…</g>             <!-- 局部描摹路径 -->
  <g id="text" font-family="…">…</g>
</svg>
```

原则：

- 默认不出现整图 `<image>`；照片/头像嵌入时只出现小裁剪 `<image>`。不出现 `<filter>`/`linearGradient`；
- 不用外部字体/图片 URL；
- 文本转义、`xml:space="preserve"`；
- `shape-rendering="geometricPrecision"`；
- 可选 `<title>`/`<desc>`，但**不要**写原文件名（原型早期用 `src.stem`，已改为通用标题）。

## 5. 三个核心难点的深入分析

### 5.1 SVG 算法：什么时候“描”，什么时候“画”

| 元素 | 推荐表示 | 原因 |
| --- | --- | --- |
| 背景/面板/气泡/卡片 | `<rect rx>` | 小、精确、可编辑 |
| 文字 | `<text>`（默认）/ `<path>`（可选） | 可复制/可搜索 vs 跨端一致 |
| 线性图标 | `<path>` 分色层 | 低分辨率下也够用 |
| emoji | `<path>` 分色层；未来 Unicode + 字体 | OCR 不识别 emoji |
| logo | 局部描摹 or 图标库吸附 | 品牌形状复杂但面积小 |
| 照片/头像 | `--photos embed` 裁剪嵌入 / `placeholder` 占位 | 还原 vs 隐私/体积的显式取舍 |
| 阴影/渐变 | 1px 半透明边 or 纯色近似 | 用户明确说不要渐变 |

纯 tracer 的问题是“它不知道什么是文字”。把文字描成 path 会：
文件大、不可编辑、无法复制、抗锯齿边缘产生大量小路径。语义重绘把文字交给 OCR，
才能在 1080×2306 上做到 39 KiB（占位）/ 111 KiB（嵌入照片）的级别。

### 5.2 OCR：选型与工程细节

| 引擎 | 平台 | 中文 | 框粒度 | 隐私 | 备注 |
| --- | --- | --- | --- | --- | --- |
| Apple Vision | macOS | 很好 | 行 | 本地 | 默认；无需 key；`zh-Hans` |
| PaddleOCR | 全平台 | 很好 | 行/词/字 | 本地 | 重，模型多；适合服务端 |
| RapidOCR | 全平台 | 好 | 行/词 | 本地 | ONNX，部署轻 |
| Tesseract | 全平台 | 一般 | 词 | 本地 | 小字/中文弱 |
| Windows OCR | Windows | 好 | 行/词 | 本地 | 系统 API |
| 云 OCR/多模态 | 云 | 最好 | 字/词 | 上传风险 | 不建议默认 |

工程建议：

- **行级框足够做第一版**；需要精确字距/混排样式时再上词/字框；
- **置信度要保留**：低置信度的短 ASCII 行很可能是图标误识别；
- **不要自动“纠正”文本**：漏字母、数字串/按钮标签错误应留给人工/编辑器；
- **保留 scene JSON**：OCR 是唯一的“语义输入”，人工改一次比重新跑 CV 便宜；
- **未来**：用第二 OCR 引擎对低置信行做交叉验证；或用小型 VLM 只做“这是文字还是图标”的二分类。

### 5.3 手机字体渲染还原

- **字号**：用墨迹宽度，不用 OCR 框高度；
- **基线**：用字体 ascent + 墨迹 bottom，不用框底；
- **字重**：用墨迹密度 + IoU，小字号限重；
- **字族**：候选渲染 + 整图投票；不要指望单行判断；
- **跨端**：默认 font stack；需要绝对一致时转 path；
- **授权**：PingFang/微软雅黑不可再分发；Noto/Source Han 是 OFL；
- **移动端**：Android 常见 Noto Sans CJK/Roboto，iOS PingFang SC；
  厂商/App 自定义字体只能靠候选库或人工指定。

一个容易忽略的点：**CJK 字体的 advance 基本都是 1em**，所以“宽度匹配”不能识别
字体，只能识别字号。字体识别必须看形状（掩码 IoU / 特征），这也是为什么原型里
字族投票和字重选择要分开做。

## 6. 隐私与安全分析

### 6.1 这个工具能去掉什么

- 整张原始像素网格：不嵌入、不引用；照片/头像只在显式 `--photos embed` 时嵌入小裁剪；
- 平坦区域的 ±1~2 抖动：条件中值 + 调色板量化后消失；
- LSB/像素级水印：重绘区域不再有对应的原始像素；但 `--photos embed` 的裁剪仍保留照片像素；
- EXIF/JPEG 元数据：输出是 SVG 文本，不继承；
- 照片/头像内容：默认随裁剪嵌入；`--photos placeholder` 时变占位块。

### 6.2 不能去掉什么

- **可见文本内容**：姓名、订单号、价格、地址仍会以 `<text>` 出现；
- **logo/品牌/布局**：仍可识别；
- **粗粒度颜色/字体/尺寸**：仍是指纹；
- **OCR 的零宽字符/隐藏 Unicode**：原型会去掉 `Cf` 类字符，但其他同形字仍需检查；
- **文件名/标题**：不要写入 SVG；原型的 `<title>` 已改为通用文本；
- **二维码/条形码**：如果没被 OCR/照片遮住，可能被描摹或保留为图标。

### 6.3 威胁模型建议

- 默认 `photos=embed`（用户要求还原）；提供 `--photos placeholder` 作为隐私模式；
- 输出前跑一次“敏感信息扫描”（正则：手机号、订单号、地址、邮箱、身份证）；
- 提供“纯线框模式”（`--style wireframe`）：所有面板白底灰线、文字/图标单色，进一步降低颜色指纹；
- 明确文案：**“去像素隐写” ≠ “匿名化”**。

## 7. 评估方法与当前结果

### 7.1 当前结果

把 SVG 用 `@resvg/resvg-js` 栅格化回原尺寸，再跑同一 OCR，按中心点最近匹配：

| 图 | 原 OCR 行 | 重绘后 OCR 行 | 匹配行 | 中心误差中位数 | 文本相似度均值 | SVG 大小 |
| --- | --- | --- | --- | --- | --- | --- |
| `1.png` 602×842 | 20 | 20 | 18 | **1.50 px** | **0.988** | 76 KiB (hybrid+flat+embed) |
| `2.jpg` 1080×2306 | 38 | 38 | 37 | **3.57 px** | **0.980** | 111 KiB (hybrid+flat+embed) |

补充模式（同一套几何，文字不变）：

| 图 | 模式 | SVG 大小 | 说明 |
| --- | --- | --- | --- |
| `2.jpg` | wireframe + embed | ~92 KiB | 白底灰线、照片灰度嵌入 |
| `2.jpg` | fast + placeholder（无字体投票/图标） | ~7 KiB | 约 1.5 s |
| `2.jpg` | placeholder | ~39 KiB | 不嵌入照片 |

说明：

- 像素级参考：`tools/compare.py` 在最终渲染上给出 SSIM ≈ 0.90（1.png）/ 0.88（2.jpg），
  主要用于看 diff 热图；嵌入照片/字体差异会压低数值；
- 这个指标偏向“文本层是否还在正确位置”，不衡量照片/图标；
- `1.png` 有 2 行未匹配，是重绘后 OCR 把相邻行合并/拆分的匹配问题，视觉上两行都在；
- 文件大小：`2.jpg` 从 602 KiB 降到 111 KiB（嵌入照片后仍远小于原图）；纯占位约 39 KiB。
- 产品图裁剪会向上并入附近的标题文字，因此比纯照片略大；照片内的文字不再重复输出，
  而是作为图片内容保留（不可单独选中）。

### 7.2 建议的正式 benchmark

手工截图很难有 ground truth。建议做合成基准：

1. 用固定 HTML/Flutter 页面渲染 100 张截图，记录 DOM/Widget 的 bbox、字号、颜色；
2. 覆盖：中英混排、emoji、头像、图片、深色模式、2x/3x DPR、JPEG/PNG；
3. 指标：
   - 文本 CER/WER；
   - 行中心误差、基线误差、字号误差；
   - 面板 IoU；
   - 颜色 ΔE（只对主色）；
   - SSIM/PSNR（仅参考，照片嵌入/占位都会影响）；
   - SVG 大小、元素数、路径点数；
   - 隐私：SVG 中是否出现 `<image>`、EXIF、零宽字符、原始文件名。

## 8. 相关工具/研究（可复用与不建议）

- **矢量化**：vtracer（彩色分层，适合图标/logo）、potrace（单色）、ImageTracer.js、SVGcode；
- **截图理解**：OmniParser、ScreenAI、UIED、UI-TARS、Florence-2；
  适合“元素检测/图标分类”，但重量级，且对精确坐标/文字不如 OCR+CV；
- **OCR**：Apple Vision、PaddleOCR、RapidOCR、Tesseract、Windows OCR；
- **字体识别**：DeepFont 类研究、候选字体渲染匹配；工程上后者更可控；
- **端到端矢量生成**：StarVector、diffvg/LIVE；目前不适合精确 UI；
- **截图转代码**：screenshot-to-code 类项目；语义强、几何弱、隐私风险；
- **几何拟合**：Primitive（用椭圆/矩形拟合图像）；可用于图标/背景，但不处理文字。

结论：**复用局部描摹（vtracer/potrace）+ OCR + 自研布局/文本拟合**，不要端到端。

## 10. 需要你拍板的几个决策

1. **默认风格**：扁平彩色（当前默认）还是纯线框？（两者都已实现）
   （线框更隐私、更像草图；彩色更还原。）
2. **照片/头像**：默认嵌入裁剪（当前，按你的要求）还是默认占位？隐私优先时建议占位。
3. **文本**：默认 `<text>` 还是直接转 path？
   （`<text>` 可复制/可编辑；path 跨端一致但不可编辑。）
4. **目标渲染器**：浏览器/Figma/Illustrator/Inkscape 哪一个是“第一优先”？
   这决定字体栈、`textLength`、`dominant-baseline` 的策略。
5. **字体授权**：是否接受只使用 OFL 字体做嵌入/转 path？
6. **跨平台优先级**：macOS 先跑通，还是尽快上 Windows/Linux OCR？

## 11. 原型的已知问题（诚实清单）

- OCR 对按钮标签/数字串的误识别：原型不猜，保留原始结果；请用 scene JSON 修。
  Vision-only 对某些数字串会错，默认 `auto` 在装有 RapidOCR 时走 hybrid 交叉校验。
- 图标是低分辨率描摹，细节会“糊”；小图标可能被合并/漏掉。
- 头像/logo/emoji 的分类是启发式，偶尔会把按钮图标当头像（或反之）。
- 阴影/渐变全部近似为纯色/1px 边。
- 字体族投票按整图平均，标题/正文混用不同字族时只能选一个。
- `1.png` 的有效分辨率只有 301×421，图标本身信息不足，描摹上限很低。
- 输出不含整张原始位图，但**文本内容和嵌入的照片裁剪仍然可见**；分享前请人工检查。
- 默认 `--photos embed` 是按本轮需求选择的“还原优先”；隐私优先时请显式
  `--photos placeholder`，并考虑 `--photo-scrub`（丢弃 2 个 LSB）或 `--style wireframe`。
- hybrid OCR 依赖可选的 `rapidocr_onnxruntime`；未安装时自动退化为 Vision 或 RapidOCR。

## 13. 对 `docs/idea-by-grokbot.md` 的对照结论

这份调研与当前原型的方向一致：**混合 SVG（矢量 chrome + 真文本 + 照片裁剪）**，
而不是整图 tracer。可直接落地的点：

| Grokbot 建议 | 当前状态 | 决定 |
| --- | --- | --- |
| 混合 SVG：rect/path + `<text>` + `<image>` | 已实现 | 保持 |
| 照片/头像裁剪后嵌入 | 已实现（默认 embed） | 保持，保留 placeholder/outline |
| 文本保持 SVG text | 已实现 | 保持 |
| 2x/3x 截图、去噪、posterize | 已实现（去抖 + 调色板 + 2x 分析） | 保持 |
| 圆角/描边/分隔线结构 | 面板 + `strokes.py`（默认 auto，只保留长分隔线/边框） | 已接入，低置信度丢弃 |
| 渐变用 SVG stops 或 raster patch | 原型 `caption_svg/gradients.py` 已通过合成测试；`tests/2.jpg` 的浅色背景 tile 也有 7 个高置信命中 | 未接入：渐变背景会破坏调色板面板分割，需要 gradient-aware segmentation 后再开 CLI |
| 图标库吸附 | 当前局部描摹 | 研究可行性，低置信度回退描摹 |
| 阴影/毛玻璃保留 raster patch | 未做 | 可选，未来 |
| 视觉 diff / side-by-side | 已加 `tools/compare.py` | 保持 |
| SVGO 优化 | 未做 | 低优先级；当前体积可接受 |
| DOM importer / html.to.design | 不适用截图管线 | 不做 |
| 整图 AI SVG / 纯 tracer | 不适合精确 UI | 不做默认 |

结论：**分隔线已接入**（`strokes.py`，默认只保留长分隔线/边框）；渐变检测原型已通过
合成测试但**尚未接入**，因为渐变背景会破坏当前调色板面板分割，需要先做
gradient-aware segmentation；图标库匹配先做可行性研究。不做 DOM/端到端，不把
“去像素隐写”说成匿名化。
